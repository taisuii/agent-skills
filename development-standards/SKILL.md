# Development Standards - 开发规范

## 核心原则

在所有开发工作中遵循以下原则：

1. **三思而后行**：编码前先评估可行性和预期效果，避免盲目实现导致大量回退
2. **了解再决策**：不熟悉的代码先阅读理解，不要凭猜测做决策
3. **需求优先**：充分理解用户需求，发现不清晰或矛盾之处主动提问
4. **专业开发者视角**：不仅是让代码能跑，而是写出可维护、有远见的代码
5. **运行管理原则**: 不要一直尝试运行，但是可以尝试构建和编译，因为是多agent开发，多次运行导致端口多次被占用，导致协作困难

## 代码架构与质量

### 大局观与可维护性

**禁止"堆屎山"式开发**：
- ❌ 随意添加功能导致结构混乱
- ❌ 无规划的补丁式修复
- ✅ 先理解现有架构，再决定如何融入新功能
- ✅ 保持代码库整洁、结构清晰

### 模块化与耦合度

**原则**：
- 功能按领域/职责划分模块
- 模块间通过明确接口交互
- 避免循环依赖和过度耦合

**检查清单**：
- [ ] 新功能是否属于现有模块，还是需要新建模块？
- [ ] 模块依赖是否单向且必要？
- [ ] 接口是否清晰且稳定？
- [ ] 修改一个模块是否会波及多个不相关模块？

### 文件组织原则

**禁止随意创建文件**（"随地大小便"）：
- ❌ 根目录堆积测试文件
- ❌ 到处创建临时脚本和文档
- ✅ 遵循项目既定目录结构
- ✅ 测试、文档、脚本各归其位

**标准目录示例**：
```
src/           # 源代码
  components/  # 组件
  utils/       # 工具函数
  types/       # 类型定义
tests/         # 测试文件
docs/          # 文档
scripts/       # 脚本工具
```

## 重构与大规模改动

### 重构前置检查

**必做步骤**：
1. **明确需求**：重构要解决什么问题？
2. **评估影响范围**：会影响哪些模块和功能？
3. **确认可行性**：是否有技术风险或不可逆操作？
4. **理解现有代码**：为什么现在是这样实现的？

### 重构执行原则

- **不要害怕大幅改动**：如果需求明确且有必要，大胆重构
- **需求为本**：为了正确的目标，可以推翻现有实现
- **不省略细节**：每个边界情况、错误处理都要考虑
- **先捋清楚再改**：不懂的地方主动询问，不要猜

### 重构模式

**增量式重构**（小改动）：
1. 添加新实现（不破坏旧功能）
2. 迁移调用方
3. 移除旧实现

**推倒重建**（大改动）：
1. 在分支中完成新实现
2. 确保测试覆盖
3. 一次性切换
4. 保留回滚方案

## UI/UX 设计规范

### 配色与视觉

**禁止**：
- ❌ 蓝紫渐变配色
- ❌ Emoji 表情作为图标
- ❌ 为了丑陋的 UI 写大量样式代码

**推荐**：
- ✅ 简约、大气的设计
- ✅ 优先使用成熟的组件库（Ant Design、Material-UI、shadcn/ui）
- ✅ 优先使用专业图标库（Lucide、Heroicons、Phosphor Icons）
- ✅ 使用设计 token/主题系统保持一致性

### 布局原则

**核心思想**：简约、优雅、高效

- **组件少时**：清晰的层级和间距
- **组件多时**：分类、分页、可折叠、搜索过滤
- **禁止堆砌**：过多内容要组织，不要一股脑展示

**布局检查清单**：
- [ ] 是否有清晰的视觉层级？
- [ ] 是否响应式适配移动端？
- [ ] 信息密度是否合理（不过分拥挤或空旷）？
- [ ] 交互是否直观（用户能快速找到操作入口）？

### 一致性与可访问性

**设计一致性**：
- 颜色、字体、间距使用 token 统一管理
- 相同类型组件保持相同样式和交互
- 建立设计系统或遵循现有组件库规范

**响应式设计**：
- 移动端、平板、桌面端适配
- 使用弹性布局（Flexbox/Grid）
- 关键断点：375px（手机）、768px（平板）、1024px+（桌面）

**可访问性（a11y）**：
- [ ] 颜色对比度达到 WCAG AA 标准（4.5:1）
- [ ] 键盘可完全操作（Tab、Enter、Esc）
- [ ] 语义化 HTML（正确使用 button、nav、header 等）
- [ ] 为图标和图片提供 alt 文本或 aria-label

## 代码质量工具链

### 必须一键通过

所有代码提交前必须满足：
```bash
# Formatter（格式化）
npm run format    # 或 prettier --write .

# Linter（代码检查）
npm run lint      # 或 eslint . --fix

# Type check（类型检查）
npm run typecheck # 或 tsc --noEmit
```

**零容忍原则**：
- ❌ 不要提交有 lint 错误的代码
- ❌ 不要忽略类型错误（any 是技术债）
- ✅ CI/CD 中自动执行这些检查

### 代码风格一致性

**目标**："读起来像一个人写的"

- **命名规范**：
  - 变量/函数：camelCase
  - 类/组件：PascalCase
  - 常量：UPPER_SNAKE_CASE
  - 文件名：kebab-case 或 PascalCase（根据项目约定）

- **目录结构**：
  - 按功能/领域组织，而非文件类型
  - 相关文件放在一起（colocation）

- **错误处理风格**：
  - 统一使用 try-catch 或 Result 类型
  - 错误有明确的类型和错误码
  - 不要吞掉错误（silent failure）

## 工程实践

### 性能意识

**性能预算**：
- 首屏加载 < 3s（3G 网络）
- 交互响应 < 100ms
- 动画 60fps

**识别瓶颈**：
- 使用浏览器 DevTools Profiler
- 监控关键指标：LCP、FID、CLS
- 避免过早优化，但要知道性能瓶颈在哪

### 错误处理

**清晰的错误链路**：
```typescript
// ✅ 好的错误处理
class AuthenticationError extends Error {
  code = 'AUTH_FAILED';
  statusCode = 401;
}

try {
  await login(credentials);
} catch (error) {
  if (error instanceof AuthenticationError) {
    // 明确知道如何处理
  }
  throw error; // 不吞掉未知错误
}
```

**错误码规范**：
- 定义清晰的错误码体系
- 错误信息对开发者友好（包含上下文）
- 用户看到的错误信息要人性化

### 可观测性

**日志**：
- 关键操作记录日志（用户登录、支付、数据修改）
- 日志包含：时间戳、用户 ID、操作类型、结果
- 区分日志级别：DEBUG、INFO、WARN、ERROR

**指标与追踪**：
- 监控核心业务指标（注册量、活跃用户、错误率）
- 追踪系统能定位线上问题（trace ID 贯穿请求链路）
- 定期审查指标，发现异常及时处理

## 需求理解与沟通

### 需求澄清检查清单

在开始实现前，确认：

- [ ] **目标清晰**：要解决什么问题？为谁解决？
- [ ] **边界明确**：哪些在范围内，哪些不在？
- [ ] **优先级**：核心功能 vs 附加功能
- [ ] **约束条件**：性能要求、兼容性、安全性
- [ ] **验收标准**：如何判断完成？

### 主动提问的场景

**必须提问**：
- 需求描述模糊或自相矛盾
- 实现方案有多种选择，各有利弊
- 需要做架构级决策（影响长远）
- 发现潜在的逻辑漏洞或边界问题

**提问模板**：
- "我理解的需求是 [X]，是否正确？"
- "这里有两种方案：[A] 和 [B]，各有优劣，您倾向哪种？"
- "如果出现 [边界情况]，应该如何处理？"

## 实施工作流

### 开发前（5 分钟思考）

1. **理解需求**：阅读需求描述，识别不清晰之处
2. **评估可行性**：技术上能否实现？有无风险？
3. **设计方案**：如何在现有架构中实现？需要改什么？
4. **预测效果**：实现后会达到什么效果？有无副作用？

### 开发中

1. **小步提交**：功能可分解为多个小步骤，每步都可工作
2. **持续验证**：边写边测，不要写完一大堆再测
3. **保持整洁**：删除调试代码、注释掉的代码、无用导入
4. **自我审查**：提交前再看一遍 diff，检查是否有遗漏

### 开发后

1. **功能测试**：正常流程、边界情况、错误处理
2. **代码检查**：lint、typecheck、格式化
3. **文档更新**：如果改了 API 或行为，更新相应文档
4. **团队审查**：Pull Request 描述清晰，等待 code review

## 快速参考

### 代码质量自查

提交前问自己：
- 代码是否清晰易懂？（6 个月后的自己能看懂吗？）
- 是否有重复代码可以抽取？
- 错误处理是否完善？
- 是否有类型安全保证？
- 性能是否合理？（无明显瓶颈）

### 架构设计自查

设计时问自己：
- 职责是否单一？（每个模块/函数只做一件事）
- 依赖方向是否合理？（高层依赖低层，不反向）
- 接口是否稳定？（改实现不影响调用方）
- 是否易于测试？（能轻松编写单元测试）

### UI 设计自查

设计界面时问自己：
- 是否简洁且专业？（不花哨、不幼稚）
- 是否使用了成熟的组件库和图标库？
- 布局是否响应式？
- 交互是否符合用户预期？

## 总结

遵循这些标准的核心目的是：**写出专业、可维护、有远见的代码**。

不要为了快速完成任务而牺牲质量，从长远来看，高质量的代码会节省大量维护成本。

记住：**你是专业开发者，不是代码搬运工。**
